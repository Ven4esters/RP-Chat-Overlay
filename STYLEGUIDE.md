# Styleguide проекта / Project Styleguide

Единый стандарт оформления кода для Chat&AutoAnimations RP Overlay. Все правила проверяются
автоматически: линтером `ruff`, форматером `ruff format`, типами `mypy`.

## 1. Базовые принципы чистоты кода

- **Читаемость важнее «умности»**. Код пишется для людей, компилятор — вторичен.
- **KISS, DRY, YAGNI, SOLID** — ориентиры, не религия. Не создавайте абстракцию «на будущее».
- **Явное лучше неявного**: зависимости, побочные эффекты, ошибки, контракты — явно.
- **Одна ответственность**: модуль/класс/функция решают одну задачу.
- **Маленькие функции**: ориентир — до 30–40 строк и до 3–4 уровней вложенности; если больше — декомпозируйте.
- **Цикломатическая сложность**: ориентир ≤ 10–15 на функцию.
- **Никакого мёртвого кода**: нет закомментированного кода, «временных» флагов, TODO без тикета.
- **Магические числа и строки** — в константы/конфиг с понятными именами.
- **Неизменяемость по умолчанию**, где уместно; минимум глобального состояния.
- **Явная обработка ошибок**, никаких «проглоченных» исключений.
- **Границы приложения валидируют вход**: не доверяйте пользователю, сети, внешним API.

## 2. Стиль и форматирование

- **Formatter и linter в CI**: `ruff` + `ruff format`. Автоформатирование обязательно.
- **Длина строки**: 100 символов (`ruff.toml`). Для файлов-данных (`i18n.py`, `glossary_data.py` и т.д.) E501 отключён точечно — длинные строки интерфейса — это данные, не код.
- **Импорты**: отсортированы, неиспользуемые удалены.
- **Публичные API**: явные типы/контракты, где язык это позволяет.

### Именование

| Сущность | Стиль | Пример |
|---|---|---|
| Классы / типы | PascalCase | `SettingsWindow`, `DlxService` |
| Функции / переменные | snake_case | `dlx_translate`, `ui_lang` |
| Константы | UPPER_SNAKE_CASE | `PORT_RANGE`, `MAX_CHARS` |
| Булевы | is/has/can/should | `is_enabled`, `has_action`, `can_translate` |
| Сокращения | без, кроме общепринятых | `id`, `url`, `http`, `dlx` |

### Файлы и пакеты

По смыслу, не `utils2`, `common`, `misc`. Модуль — одна ответственность.

## 3. Комментарии и докстринги

- **Двуязычные (RU + EN)** — каждый комментарий и докстринг на двух языках.
- **Объясняют «почему», а не «что»** — код говорит сам за себя.
- **Докстринги на публичные функции/классы/модули** с параметрами, возвратом, ошибками.

Пример:
```python
def translate(self, text: str, source: str = "auto", target: str = "IT",
              timeout: float = 8.0) -> str:
    """Перевести текст через локальный сервис / translate via the service.

    «auto» не передаётся как source_lang: DeepL не принимает такое значение.
    Для автоопределения языка параметр source_lang просто опускается.
    "auto" is not sent as source_lang: DeepL rejects it. For auto-detect,
    the source_lang parameter is omitted entirely.
    """
```

## 4. Обработка ошибок и логирование

- **Единая модель ошибок**: кастомные исключения (`DlxError`, `TranslateError`) с контекстом.
- **Не логируйте секресы, токены, пароли, PII**.
- **Логи структурированные**, с уровнями DEBUG/INFO/WARN/ERROR.
- **Ошибки не глотать**; добавляйте контекст при пробросе.
- **Различайте ожидаемые бизнес-ошибки и технические сбои**.
- **Fail fast на старте**: проверка конфигурации, зависимостей.
- **Таймауты обязательны** для всех внешних вызовов.
- **Не логируйте в цикле «на каждый чих»**; не используйте `print` в проде.

## 5. Безопасность

- **Валидация и нормализация входа на границе**; выход — экранирование по контексту.
- **Параметризованные запросы**; никакой конкатенации SQL.
- **Секреты** — только через переменные окружения/конфиг-файлы, не в репозитории.
- **TLS везде**; безопасные заголовки.
- **Принцип наименьших привилегий**.
- **Зависимости сканируются на уязвимости** (SCA в CI).

## 6. Тестирование

- **Пирамида тестов**: много unit, меньше integration, минимум e2e.
- **Unit-тесты детерминированы**, быстрые, без сети/БД/времени/рандома без контроля.
- **Обязательные кейсы**: happy path, границы, негативные сценарии, ошибки зависимостей.
- **Регрессионный тест на каждый исправленный баг**.
- **Тесты — часть кода**: читаемые, с понятными именами, без дублирования логики продакшена.
- **Flaky-тесты чинятся или удаляются**.

## 7. Code Review и PR

- **PR маленькие**: ориентир до 300–400 строк изменений; большие — дробить.
- **Коммиты — Conventional Commits**; сообщение объясняет смысл.
- **Ветки — по тикету**; защита основных веток.
- **Не мержить с «красным» CI, конфликтами, незакрытыми блокирующими комментариями.**
- **Минимум одно одобрение ревьюера**; для критичных модулей — два.

## 8. Definition of Done

Задача считается выполненной, только если:

- код соответствует стайлгайду и прошёл линтеры/форматтеры;
- есть тесты на новое поведение и регрессию;
- CI зелёный, quality gates пройдены;
- ревью выполнено;
- документация/CHANGELOG обновлены, если нужно;
- миграции и конфиг проверены;
- нет новых критичных уязвимостей и секретов;
- понятен план отката/включения фичи;
- выполнены нефункциональные требования: производительность, безопасность, доступность.
